Architecture

Render Monitor is a two-tier application: a React SPA and an Express backend that proxies the Render API. This page explains the proxy model, the data flow, and the security boundaries.

The proxy model

Every request from the browser is routed to the backend under /api/render/*. The backend attaches your Render API key as a bearer token and forwards the request to https://api.render.com/v1. 

┌──────────────┐        ┌────────────────────┐        ┌────────────────────┐
│   Browser    │  HTTP  │   Backend (Express)│  HTTPS │  Render REST API   │
│  React SPA   │ ─────► │  /api/render/*     │ ─────► │  api.render.com/v1 │
│              │        │                    │        │                    │
│              │   WS   │                    │  WSS   │                    │
│              │ ─────► │ /logs/stream       │ ─────► │ /logs/subscribe    │
└──────────────┘        └────────────────────┘        └────────────────────┘
                              │
                              └─ RENDER_API_KEY (server-side only)

The key is a single, centralized concern in server/src/renderApi.ts. Every route in server/src/routes.ts builds a query, delegates to renderApi(), and returns the JSON response untouched.

The frontend never knows the key exists. Its only configuration is the backend base URL (VITE_API_URL) and the WebSocket origin (VITE_WS_URL).

Why the API key stays server-side

A Render API key can read every service, deploy, log, and metric across your account. If it were embedded in the frontend bundle, anyone who opened DevTools could extract it.

Render Monitor avoids that by construction:

  • The key lives only in the backend environment as RENDER_API_KEY.
  • The browser makes requests to your own backend, never to api.render.com.
  • All responses are proxied through and sanitized by omission — the backend exposes only the endpoints it defines.
✓

Read-only by design

The route table contains only GET handlers. The proxy helper supports other methods, but no write route is exposed, so the dashboard cannot deploy, scale, or delete anything.

Data flow by feature

Each page maps to a small set of Render API calls:

Feature Backend endpoint(s) Render API call
Dashboard /services, /services/:id/deploys List services; latest deploy per service.
Services /services List all services.
Service detail /services/:id, /:id/deploys, /:id/events Service, deploys, and events.
Deployments /services → /services/:id/deploys Fans out across services for recent deploys.
Deployment detail /deploys/:id?serviceId= Single deploy lookup.
Logs /logs, /logs/values, WS /logs/stream Historical log query, filter values, live subscription.
Metrics /metrics/* Time-series metrics per resource.
Settings /connection/status Lightweight /services?limit=1 probe.

Workspace resolution

Log queries require an ownerId. When the caller doesn’t provide one, the backend resolves the default workspace by calling /owners and caches the result for the process lifetime (server/src/owners.ts). If the key spans multiple workspaces, the backend refuses to guess and asks for an explicit ownerId.

Log streaming

Live logs use a WebSocket proxied at /api/render/logs/stream. The flow is:

  1. The browser opens a WebSocket to your backend with the same query parameters as a log query.
  2. The backend opens a connection to wss://api.render.com/v1/logs/subscribe with the bearer token.
  3. Messages flow one way: Render → backend → browser. Client messages are ignored.
  4. When Render closes the stream, the backend closes the browser socket with a normal close code.
ℹ

The stream is unidirectional by design — Render’s log subscription API does not accept client messages.

Tech stack

Frontend

  • React 18 + TypeScript
  • Vite build tooling
  • Tailwind CSS design tokens
  • TanStack Query for data fetching
  • Recharts for metric charts
  • React Router for navigation

Backend

  • Node.js + Express
  • TypeScript (ES modules)
  • ws for the WebSocket proxy
  • Undici for outbound HTTP
  • dotenv for configuration
  • CORS enabled for local development

Security considerations

  • CORS is open. The backend enables CORS for all origins. If you host it publicly, restrict this to your frontend origin to prevent third parties from piggybacking on your key.
  • The backend is unauthenticated. Anyone who can reach it can read your Render data. Keep it private, behind your frontend host, or add authentication before exposing it on the public internet.
  • Rate limits are shared. All browser users share one API key, so heavy use consumes a single Render rate-limit budget. The proxy surfaces rate-limit errors back to the client.
  • Error stacks are dev-only. Stack traces are included in error responses only when NODE_ENV=development.
⚠

For a public deployment, add authentication in front of the backend and lock down CORS. Render Monitor is designed as a trusted internal tool.
